## Trap captured (step-2 evidence, unmodified stage-3 build)

Exactly the predicted GQA-prefill failure, though it fires **host-side
before the device trap can**: the launcher's smem-ceiling bump is rejected
by HIP because the tensor-core kernel's 96 KiB dynamic arena exceeds
gfx906's 64 KiB/CU LDS limit:

```
/src/src/ops/launcher/gqa_attention_prefill.cu:26:
  CUDA_CHECK(attr_bf16) failed: hipErrorInvalidValue: invalid argument
```

(exit 134/SIGABRT, immediately after weight load; `stage4-run1.log`,
untracked). The `__builtin_trap` ldmatrix/mma stubs in the kernel body were
therefore never reached — the launch never happened.

## The wave64 prefill kernel

`src/ops/kernel/gqa_attention_prefill_bf16_gfx906.cuh`:
`gqa_attention_prefill_simt_bf16_kernel` — same template surface and
argument list as the tensor-core kernel; the launcher
(`gqa_attention_prefill.cu`, under `NINFER_GFX906_COMPAT`) swaps grid
geometry to Br = 32 query rows/CTA and passes **no dynamic smem** (static
~48.4 KiB LDS arena instead — under the 64 KiB/CU limit that killed the
original). Design, correctness-first per the stage-4 plan:

- FlashAttention outer loop over 32-key tiles; K and V tiles staged
  cooperatively (coalesced) into LDS, the CTA's Q rows staged once. A
  32-key tile never straddles a KV page (page size 64), so one
  `block_table` lookup per tile suffices.
- Within a tile, each logical 32-lane warp owns up to 8 query rows
  round-robin: per row, one key per lane with a serial bf16x2 dot product
  (phase A), online softmax via the logical-warp shuffle reductions from
  the stage-1 shims (phase B — `exp2_approx`/Log2E arithmetic copied
  verbatim from the decode draft), probability-broadcast P·V read from the
  LDS V tile (phase C). Bottom-right causal alignment preserved (query row
  i sees keys `[0, base_pos + i]`); tail rows `[tokens, width)` zeroed
  exactly as the original.
- LDS rows padded by 2 bf16 (129-dword stride → conflict-free per-lane row
  walks); all LDS traffic is 4-byte `__nv_bfloat162` because the padded
  516-byte row stride only guarantees 4-byte alignment.
- No ldmatrix, no mma, no cp.async. DPP ladders, half-wave pairing,
  K-reuse across the q-head group: stage-10 tuning items.
- The fill (KV-append) kernels needed no change — they were already
  mma-free and run as-is.
- int8-KV prefill attention now **throws** a clear error under compat
  instead of dying in `hipFuncSetAttribute` (port-order step 7).

## Bugs fixed / incidents (symptom → cause)

1. **Build config failure** — `CMake 3.28 or higher is required` →
   auto-rebuilt `ninfer-rocm:6.4.1` image carried Ubuntu's CMake 3.22;
   fixed in `Dockerfile.ninfer` (pip CMake 3.31), image rebuilt.
2. **First long-prompt run hung the GPU** (`HW Exception … GPU Hang` at 49%
   of weight H2D, before any ninfer kernel ran) → **not a kernel bug**:
   dmesg shows a burst of `init_user_pages: Failed to get user pages: -1`
   then `ring page0 timeout` (SDMA paging ring) — pinned-memory
   registration failing in the window right after `docker stop llama`
   released its ~24 GB. amdgpu BACO reset recovered the card without a
   reboot; the identical command succeeded cleanly on retry.
   **Operational note: give the box a few seconds between stopping the
   llama container and launching a ninfer load.**
3. The prefill kernel itself and the stage-3 decode DRAFT had **zero
   hardware bugs**: first execution of both produced the correct milestone
   outputs. The decode draft's UNVALIDATED marker can be dropped for the
   bf16 T=1 eager path (validated here); its verify/multi-batch/masked
   forms remain unexercised (no `--spec` runs yet).
